# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

A Laravel + Inertia.js (Vue 3) Document Routing System ("DepEd DART") for a Schools Division Office (SDO). It tracks two parallel document workflows — **outgoing** documents through a review/approval chain, and **incoming** documents through a routing/dispatch-and-acknowledge process — plus PKI-based digital signing of approved outgoing documents.

**Terminology note**: this codebase was originally built for a Regional Office and adapted for an SDO deployment. Internally, role slugs (`rd`, `ard`), status enum values (`pending_rd_review`, `is_rd_routing`), method names (`isOrdSecretary()`, `isOrdUnitHead`/`isDirectRoutableUnitHead`), and the division code `'ORD'` (assigned to this SDO's Office of the Schools Division Superintendent) were **deliberately left unchanged** rather than renamed throughout the codebase — renaming them would mean touching 10+ call sites for what's ultimately a cosmetic detail invisible to end users, since `code` is an internal wiring identifier, not a displayed label (see "Divisions" below). Wherever this document or the code says "RD"/"Regional Director", read it as **SDS (Schools Division Superintendent)**; "ARD"/"Assistant Regional Director" as **ASDS (Assistant Schools Division Superintendent)**; "ORD" as **OSDS (Office of the Schools Division Superintendent)**. User-facing labels (role dropdowns, page text, PDF signature metadata) have already been updated to say SDS/ASDS/etc. — only internal identifiers and this document's own prose still say RD/ARD/ORD. Seeded divisions are OSDS (code `ORD`), CID (Curriculum Implementation Division), and SGOD (School Governance and Operations Division) — see `database/seeders/DivisionSeeder.php`; this SDO's admin adds any sub-units via Office Management.

**This is Laravel + Inertia + Vue, not Livewire.** There is no `app/Livewire` directory; all interactive pages are Vue SFCs under `resources/js/Pages/**` rendered via `Inertia::render()` from standard Laravel controllers.

## Commands

Local dev runs under [Laravel Herd](https://herd.laravel.com) on Windows (site: `drs-app.test`). `php` is not on PATH in Git Bash — use Herd's shim (`~/.config/herd/bin/php.bat` or find it via `where.exe php`) or run commands in PowerShell instead.

- **Install deps**: `composer install` && `npm install` (or `pnpm install` — both a package-manager's dev process and npm scripts have been observed in this repo)
- **Dev servers**: Herd serves PHP automatically for `drs-app.test`. For frontend HMR run `npm run dev` (or `pnpm run dev`) separately. `composer run dev` also exists (spins up `serve` + `queue:listen` + `pail` + `vite` concurrently) if not using Herd.
- **Build frontend for production/non-HMR testing**: `npm run build` — required whenever you need the app to work without the Vite dev server running (e.g. testing over LAN/phone, since Herd's web server binds to `127.0.0.1` only and devices on the same network can't resolve `*.test` hostnames or reach that port; see "LAN testing" below).
- **Run all tests**: `composer test` (equivalent to `php artisan config:clear && php artisan test`), or `php artisan test` directly.
- **Run a single test**: `php artisan test --filter=test_method_name` or `php artisan test tests/Feature/SomeTest.php`.
- **Lint/format PHP**: `vendor/bin/pint` (Laravel Pint is installed; no `composer` script alias for it).
- **Migrations**: `php artisan migrate`. The dev DB (`.env`: `DB_CONNECTION=mysql`, `DB_DATABASE=drsdb`) has real seeded users/documents — **do not run `migrate:fresh` or reseed casually**; it will wipe working data. Tests run against an isolated in-memory SQLite DB (`phpunit.xml`), so `RefreshDatabase` in feature tests is always safe regardless of the dev DB's state.
- **Seeders**: `database/seeders/RoleAndDivisionSeeder.php` uses `firstOrCreate` (safe to re-run). `database/seeders/DivisionSeeder.php` **truncates the `divisions` table** before rebuilding it — do not re-run it against a populated DB without knowing this.

### Testing framework note
Despite `pest-testing`/Pest conventions existing elsewhere, **this project uses plain PHPUnit** (`phpunit/phpunit`, no `pestphp/pest` in `composer.json`). Tests are class-based (`extends Tests\TestCase`, `use RefreshDatabase`, `public function test_*(): void`), not Pest's `it()`/`test()` functions.

### Tailwind version note
`package.json` lists `@tailwindcss/vite: ^4.0.0` as a dependency but it is **not wired up** — the actual pipeline is classic **Tailwind v3**: `postcss.config.js` uses the `tailwindcss` PostCSS plugin, `tailwind.config.js` is the source of truth (content globs, theme, `@tailwindcss/forms` + `flowbite` plugins), and `resources/css/app.css` uses `@tailwind base/components/utilities` directives — not v4's CSS-first `@import "tailwindcss"` / `@theme`.

### Tinker gotcha
`php artisan tinker --execute="..."` hangs waiting on stdin when run non-interactively, and piping a script with a leading `<?php` tag into `php artisan tinker` fails to parse (psysh doesn't expect the opening tag). For one-off DB inspection/scripts, either redirect stdin from `/dev/null`, or — more reliably — write a standalone PHP script that boots the framework directly:
```php
require __DIR__.'/vendor/autoload.php';
$app = require_once __DIR__.'/bootstrap/app.php';
$app->make(Illuminate\Contracts\Console\Kernel::class)->bootstrap();
// ... your code, then delete the script
```

### LAN/phone testing
Herd's web server listens on `127.0.0.1` only (confirmed via `Get-NetTCPConnection`). To test on a phone or other device on the same network, run `php artisan serve --host=0.0.0.0 --port=8000` and browse to the PC's LAN IP. If `public/hot` exists (created while `npm run dev`/`pnpm run dev` is running), Blade's `@vite` directive points asset `<script>` tags at the Vite dev server's own host (often `[::1]` or `localhost`), which is unreachable from other devices — delete `public/hot` and run `npm run build` to force it back onto the built `public/build` assets when testing this way.

## Architecture

### Auth & authorization
- **Fortify** (`app/Providers/FortifyServiceProvider.php`) handles all auth views/actions, rendered as Inertia pages. **Self-registration is disabled** (`Features::registration()` is commented out in `config/fortify.php`) — users are only created by an admin via `/users`. Because of this, the stock `tests/Feature/Auth/*` tests (leftover from Breeze scaffolding) are stale and fail out of the box (404s on `/register`, redirects to 2FA setup, etc.) — this is pre-existing and unrelated to feature work, not something to "fix" reflexively.
- **Two-factor auth is mandatory** for every authenticated user: `App\Http\Middleware\EnsureTwoFactorEnabled` (aliased `two-factor.enabled`) redirects anyone without 2FA enabled to `/two-factor/setup`, applied globally to the protected route group in `routes/web.php`.
- **`App\Http\Middleware\RestrictWeekendAccess`** (aliased `weekend.restrict`) blocks all non-`rd`/`admin` users on Saturday/Sunday, also applied globally — **unless** the user's `can_login_weekends` column is `true` (disabled by default; an admin-only per-user override toggled from the Users list via `POST users/{user}/toggle-weekend-access`, mirroring the existing `is_active` toggle pattern exactly — same `forceFill()` + `AuditLogger` + confirm-dialog UI). The toggle is hidden/moot for `rd`/`admin` themselves since they already bypass the restriction via role.
- **Spatie Laravel Permission**, single *primary* role per user via the Users admin form's single-select dropdown — `admin`, `originator`, `unit_head`, `division_chief`, `ard`, `rd`, `secretary`. **`kmt_focal` is the one exception**: a genuinely additional, layered-on-top role, toggled via its own independent checkbox in `Users/Form.vue` (never a `<select>` option) — a user keeps exactly one primary role plus, optionally, `kmt_focal` on top. `UserController::store()/update()` sync both together in one call via `rolesToSync()` (`syncRoles([$request->role, ...($request->boolean('kmt_focal') ? ['kmt_focal'] : [])])`) rather than separate assign/remove calls, so a primary-role change and a `kmt_focal` toggle can never race or drop each other. Anywhere the "primary role" is read back out for display (`UserController::index()`/`edit()`, `DocumentRoutingController`'s routing-candidate list) explicitly excludes `kmt_focal` first (`getRoleNames()->reject(fn ($r) => $r === 'kmt_focal')->first()`) rather than relying on `first()` alone, since Spatie doesn't guarantee assignment/retrieval order. `kmt_focal`'s only effect today is on `DocumentPolicy::createOutgoing()` (see below) — it has no meaning on its own without also holding `originator`.
- Authorization lives in `app/Policies/*` (`DocumentPolicy`, `DocumentRoutingRecipientPolicy`, `SigningCredentialPolicy`, `UserPolicy`). The Vue layer reads `page.props.auth.user.roles` (shared globally via `HandleInertiaRequests`) only to conditionally render UI — it is never the source of truth for access control.

### Document model — two workflows, one table
`Document` has a `type` (`DocumentType::Outgoing`/`Incoming`) and a single shared `status` (`DocumentStatus` enum) driving two independent state machines:

- **Outgoing** (originated in-house, needs approval): `draft → submitted/pending_unit_head_review → pending_division_chief_review → pending_ard_review → pending_rd_review → approved → pending_signature → signed → released` (or `for_comment`/`returned_for_revision`/`rejected` at any review stage). Each review step is a `DocumentReview` row (append-only). `OutgoingDocumentController::initialStatus()` decides the starting stage: a plain `originator` goes through unit-head review if one exists in their division, else straight to division-chief (a plain `originator` must additionally hold the `kmt_focal` role to submit at all — see `DocumentPolicy::createOutgoing()` and the Auth section above; `kmt_focal` doesn't change this routing, just the initial permission gate); a `division_chief` uploading their *own* document always skips straight to `pending_ard_review` (no one above them within their own division). A `unit_head`'s own upload only gets that same skip if they're in the ORD division tree (division code `ORD` itself, or its parent is `ORD` — e.g. ICTU/LU/PAU/ORD Proper); a unit head anywhere else has their own upload go to `pending_division_chief_review` instead. **Their chief isn't necessarily in their own division** — e.g. Procurement Unit/Personnel Section/Cash Section etc. are real sub-units (`parent_id`) of Administrative Division with their own unit head but no chief of their own; it's Administrative Division's chief who reviews them. `initialStatus()` checks both the unit head's own division and its parent for a chief (a real bug — routing straight to ARD/RD instead of the chief — until this was fixed; the fix must stay in sync with `DocumentReviewController::nextStatusAfterUnitHead()`, `DocumentPolicy::view()`/`review()`, and `DocumentScopesTrait::outgoingScope()`/`forActionScope()`/`visibleScope()`, all of which independently need the same parent-inclusive check — the scope methods specifically use `Division::selfAndChildrenIds()` so a chief's Outgoing/For Action lists include their sub-units' documents, not just exact division-id matches). The Vue "Review Chain" stepper (`Documents/Show.vue`) derives which stages to actually display from `document.reviews[].role_at_review` + current status — it does not assume a fixed 6-stage chain. Rejected is terminal; `for_comment`/`returned_for_revision` route the originator to `Documents/ResubmitOutgoing.vue`, which restarts the chain from the top. After `approved`, a **secretary** signs on the RD's behalf (see Digital signing) to reach `signed`, and after that a **Records Section** user applies a release stamp (see below) to reach `released`. **The RD's own (ORD) secretary can also originate outgoing documents** (`DocumentPolicy::createOutgoing()`) — she drafts memoranda on the RD's behalf from time to time, not just incoming mail/signing. Her own submission skips unit-head/division-chief review entirely, the same as an ORD unit head's own upload (`OutgoingDocumentController::initialStatus()` gained an `isOrdSecretary()` check, private-copy-duplicated per this codebase's usual convention, going straight to `ArdAvailabilitySetting::nextAfterDivisionChief()`) — nobody sits above her in ORD Proper except ARD/RD. A secretary outside the ORD tree does not get this ability.
- **Deleting/cancelling a document**: `DocumentPolicy::delete()` (soft delete, both types) — the RD can always delete any document. Otherwise only the document's own uploader may delete it, and only before the point where someone else's decision on it becomes authoritative: for **outgoing**, any time before `Approved` — an intermediate unit head/division chief/ARD review having already happened doesn't block it, since none of those are final, only the RD's approval is; for **incoming**, any time before it's been *deliberately* routed (excluding the auto-forward — see below). Once past that point, only the RD can remove it — **except the RD's own secretary, who may delete an incoming document she uploaded herself regardless of routing status**, including after she's personally routed it onward (e.g. to the wrong division), because she acts as the RD's delegate on her own uploads; this mirrors the RD's own unconditional delete power but is scoped to documents `isOrdSecretary()` herself uploaded — an ordinary uploader (e.g. Records Section, who can also upload incoming documents) is still blocked once a real routing exists. **The auto-forward routing on an ORD-Proper upload doesn't count as "already routed" for this check either** (for non-secretary uploaders, where the routing-status check still applies) — an ORD secretary's own incoming upload gets a `DocumentRouting` row the instant it's created (`IncomingAutoForwarder`), which would otherwise make her own document permanently undeletable from the moment she uploads it; `delete()`'s incoming branch excludes routings carrying `IncomingDocumentController::AUTO_FORWARD_REMARKS`, mirroring the identical exclusion already used by `route()`/`forActionScope()`.
- **Incoming** (received from outside, needs dispatching): `received → pending_routing → routed → completed/archived`. A `DocumentRouting` (one "action slip") has many `DocumentRoutingRecipient` rows; a recipient row targets **either** a specific `user_id` **or** an entire `division_id` (a shared assignment any member of that division can acknowledge/complete — used so a whole section, not one hand-picked person, can act). Lifecycle per recipient: `pending → acknowledged → completed`, tracked via `RecipientStatus` plus `acknowledged_by`/`completed_by`. A routing round can also be `cancelled` (see below). Normally RD/ARD/division-chief/ORD-secretary manually route incoming docs (`DocumentRoutingController`), **except** uploads by ORD Proper staff (division code `ORDP`), which auto-route to Records Section (division code `RS`) immediately on upload (`IncomingDocumentController::store()` → `App\Services\IncomingAutoForwarder::forward()`, remarks fixed to `IncomingDocumentController::AUTO_FORWARD_REMARKS` — extracted into its own service so a retroactive backfill command, see `documents:diagnose-auto-forward --apply`, can reuse the exact same routing-creation logic as a live upload). `DocumentPolicy::createIncoming()` restricts who can upload an incoming document to the `secretary` role only (narrowed from an earlier version that also allowed `originator`/`unit_head` in the ORD division tree). `DocumentPolicy::route()` limits RD/ARD/ORD-secretary to routing (issuing an action slip on) a given document **once each** — re-routing the same document a second time by the same user is blocked. That once-each check explicitly **excludes** routings with the auto-forward remarks: the auto-forward is recorded with `routed_by` set to the uploading secretary (for the audit trail — see who triggered it), but it's a system action, not a deliberate routing decision, so it must not consume that same secretary's own manual routing turn on her own upload (a real bug once secretaries gained this ability — was previously invisible because RD/ARD never upload via the ORDP path themselves). `DocumentScopesTrait::forActionScope()`'s equivalent "have I already routed this" check for the For Action queue needs the identical exclusion, or the auto-forwarded document silently disappears from the uploading secretary's own queue too. **"Already routed" is shared between the RD and her ORD secretary, not tracked per-individual** — `document_routings.is_rd_routing` (boolean) is stamped at creation time in `DocumentRoutingController::store()` (`$user->hasRole('rd') || $this->isOrdSecretary($user)`, never true for the auto-forward routing), and both `DocumentPolicy::route()` and `DocumentScopesTrait::forActionScope()` check `where('is_rd_routing', true)` instead of `routed_by = $user->id` when the caller is the RD or an ORD secretary. This is deliberately **not** re-derived from whoever currently holds the `rd`/`secretary` role+division at query time (an earlier version tried exactly that, via a `rdActingUserIds()` helper querying current role/division) — staff get reassigned (a secretary later transferred to a different division, or moved off the role entirely), and a routing she issued while she genuinely was the RD's secretary must keep counting as such forever after, regardless of where she works now; the query-time version broke the instant a secretary was reassigned, since her past routings silently stopped being recognized and reappeared in the RD's queue again (a real reported bug, fixed twice — first naively, then properly via this stamped-at-creation-time column). `php artisan documents:backfill-rd-routing-flag --apply` retroactively sets this flag on routings created before the column existed — it identifies "top-level dispatch" routings (the router was NOT themselves a recipient of an earlier routing on the same document, distinguishing an initial RD/secretary dispatch from a chief's own onward routing, again without depending on current role) and marks the ones whose router currently holds the `rd` or `secretary` role; anything else is reported as ambiguous rather than guessed at (`--also-mark-ambiguous` to force it after manual confirmation). ARD is deliberately excluded from the shared flag: she's a genuinely independent reviewer, not a delegate, so only her own `routed_by` id counts for her. `DocumentRoutingController::candidateUsers()` only offers `is_active` staff as routing candidates. **Records Section's auto-forward recipient is a courtesy copy, not a dispatched action** — `DocumentRoutingRecipientController::promoteDocumentIfFullyCompleted()` refuses to promote a document to `Completed` until at least one *real* (non-auto-forward) routing exists, even if Records Section has already acknowledged; otherwise Records Section acknowledging alone would flip the document to `Completed` before the RD/her secretary ever routes it to a division chief, and `DocumentPolicy::route()`'s status guard (`Received`/`PendingRouting`/`Routed` only) would then hide "Route Document" entirely with no real routing having happened yet — a real bug the "has a real routing" gate exists to prevent. **A division chief may cancel their own routing round** (`DocumentRoutingPolicy::cancel()`, `documents.routings.cancel`) if they picked the wrong staff and nobody has acknowledged it yet — this reverts their own assignment to `Acknowledged` (undoing the auto-close from issuing that routing) so they can route again; `DocumentPolicy::route()`'s and `DocumentScopesTrait::forActionScope()`'s "already routed" checks both exclude cancelled routings for this same reason. **The RD and her ORD secretary share this same cancel ability**, via `is_rd_routing` rather than `routed_by` — `DocumentRoutingPolicy::cancel()` lets either of them undo a routing with `is_rd_routing = true` regardless of which one of them personally issued it (mirroring how `route()`'s once-each check already treats the pair as one pool: the secretary routes *as* the RD, not independently, so either must be able to fix a mistake the other made). **Unlike a division chief, the RD/secretary's cancel ability is unconditional** — they may cancel & reroute anytime, even after the recipient has acknowledged or fully completed it, whereas a chief's own onward routing to staff stays restricted to before-acknowledgment only (a chief's routing dispatches to someone else's real work; the RD/secretary's is her own delegated authority) — mirroring the identical unconditional override already given to her for deleting her own incoming uploads (`DocumentPolicy::delete()`). If the cancelled recipient had already been `Completed` and that had promoted the whole document to `Completed` (see `promoteDocumentIfFullyCompleted()` below), `DocumentRoutingController::cancel()` reopens the document back to `Routed` so it can be routed again — otherwise `route()`'s status guard would still hide "Route Document" even after a successful cancel. `DocumentPolicy::route()`'s and `DocumentScopesTrait::forActionScope()`'s `rd`/ORD-secretary branches both also gained a `whereNull('cancelled_at')` exclusion for this — a division chief's cancel is scoped to their own `routed_by` id, no sharing. ARD and ORD unit heads have no cancel ability at all (unchanged) — ARD is deliberately excluded from the shared pool everywhere (a genuinely independent reviewer, not a delegate), and her `route()`/`forActionScope()` branches intentionally have no `cancelled_at` filter since nothing can ever set it on her routings, so adding one would be an inert no-op that misleadingly implies otherwise; unit heads simply aren't covered by this feature. **A unit head gets the exact same "forward to my own staff" ability a division chief gets if their division has `allow_rd_direct_routing = true`** — an admin-configurable per-division flag (toggled from Office Management, `DivisionController`/`Divisions/Form.vue`), not a hardcoded office list. The RD routes incoming documents to these unit heads directly, the same way she routes to chiefs (`RoutingCandidateResolver::forUser()`'s RD/ARD/secretary branch offers flagged-division unit heads alongside chiefs, but never a unit head from an unflagged division's sub-unit, e.g. Administrative Division's Records Section/Personnel Section — those are always terminal "staff" recipients, never routers themselves). ICTU, Legal Unit, and PAU (all under ORD) ship with the flag on by default (set by the migration that introduced the column, preserving what was previously a hardcoded `parent.code === 'ORD'` rule); an admin can enable it for any other unit the same way — e.g. NEAP under HRDD. A private `isDirectRoutableUnitHead()` check (division has role `unit_head` and `division.allow_rd_direct_routing` is true) is independently duplicated — matching how `isOrdSecretary()` is already duplicated per-class rather than shared — in `DocumentPolicy::route()`, `DocumentRoutingRecipientController::acknowledge()`, `RoutingCandidateResolver::forUser()` (the actual source of the candidate list both `DocumentRoutingController::candidateUsers()` and `RouteDocumentRequest::validateRecipientsAreEligible()` draw from, so those two no longer need their own copies), and `DocumentController::show()`'s `recipientMayDeferCompletion` flag — all four independently needed the identical carve-out, or a directly-routable unit head would acknowledge straight into `Completed` with no chance to route to their own staff (the original bug this fixed). A division chief's ability to route to their *own* sub-unit's head (e.g. HRDD's chief → NEAP's unit head) is unrelated to this flag — it's always available via `Division::selfAndChildrenIds()`, regardless of `allow_rd_direct_routing`.
- **The RD's own secretary** (`DocumentPolicy::isOrdSecretary()` / `DocumentScopesTrait::isOrdSecretary()` — two separate private copies of the same check, not shared, matching how `isRecordsSectionMember()` isn't shared either) — role `secretary` **and** division is `ORD` itself or a direct child of it (e.g. ORD Proper) — can route incoming documents in lieu of the RD: same blanket incoming visibility (`view()`/`incomingScope()`/`visibleScope()`) and the same once-each `route()` rule as RD/ARD. This is distinct from her existing outgoing-document rules (signing, the `Approved`-status `forActionScope()` queue), which are untouched. A `secretary` outside the ORD tree gets none of this.
- Uploaded files (both workflows) are validated with `App\Rules\PdfFile`, which checks the `%PDF-` magic byte signature in addition to the `.pdf` extension, to reject renamed non-PDF files.

Query/visibility rules for both workflows are centralized in `App\Traits\DocumentScopesTrait` (`outgoingScope`/`incomingScope`/`forActionScope`/`visibleScope`), shared by `DocumentController::index()` and `DashboardController`. Any new role-based visibility rule belongs there, not reimplemented ad hoc per controller.

### Control numbers
Every document (both workflows) gets an internal `control_number` stamped once at creation, in `App\Services\ControlNumberGenerator`, called from `OutgoingDocumentController::store()`/`IncomingDocumentController::store()` — **never** regenerated afterwards (`OutgoingDocumentController::updateResubmit()` reuses the same row/id on resubmission and deliberately never touches it). Formats: `OUTGOING-{DIVISION_CODE}-{YEAR}-{MONTH}-{SERIES}` (e.g. `OUTGOING-CLMD-2026-07-001`) and `INCOMING-{YEAR}-{MONTH}-{SERIES}` (e.g. `INCOMING-2026-07-001`). **The SERIES resets only when the YEAR changes, not monthly** — the month embedded in the string is purely descriptive of when the document was created, not a counter boundary; the counter's scope key is `(type[, division code], year)` only, so two documents from the same division/year keep incrementing across every month (a subtlety worth remembering since the string visually looks month-scoped but isn't). Division code resolution falls back from the division's own `code` to its **parent's** `code` (e.g. Legal Unit/Public Affairs Unit/ICT Unit → `ORD`; Procurement Unit/Personnel Section/Cash Section etc. → `AD`) since those sub-units were seeded without their own code (see "Divisions" below) — `ControlNumberGenerator::resolveDivisionCode()` is public specifically so the backfill command can group documents by the same code a live document of that division would get. Falls back further to a literal `'GEN'` if neither the division nor its parent has a code (no currently-seeded division should hit this). Numbers are assigned via a new `document_control_number_counters` table (one row per scope, unique on `scope`) using a MySQL `INSERT ... ON DUPLICATE KEY UPDATE last_number = LAST_INSERT_ID(last_number + 1)` atomic upsert — race-safe under concurrent submissions with no explicit locking. **This app's test suite runs on in-memory SQLite** (`phpunit.xml`), which has no equivalent expression, so `ControlNumberGenerator::next()` branches on `DB::connection()->getDriverName()` and falls back to an explicit transaction + `lockForUpdate()` there — a gotcha worth remembering if this method's behavior ever looks wrong only under tests. `documents.control_number` is nullable + unique (safe together — unlimited `NULL`s can coexist under a unique index in both MySQL and SQLite, only non-NULL duplicates are ever rejected). `php artisan documents:backfill-control-numbers` (dry-run by default, `--apply` to write) retroactively numbers documents that predate this feature, grouped/ordered by `created_at` (then `id`) per the same scope a live document would use, via the exact same `ControlNumberGenerator::next()` counter — so a new document created after the backfill runs continues the sequence with no gap or collision. Its dry-run preview calls `peek()` (read-only) rather than `next()`, so running it repeatedly, or running it and never applying, can never itself consume a series number.

### Digital signing
- `UserSigningCredential` (P12 + optional e-signature image + certificate metadata) always belongs to the **RD** (role `rd`) — looked up canonically via `UserSigningCredential::forRegionalDirector()`.
- The `secretary` role is a delegate who attaches the *RD's* signature on approved outgoing PDFs via `documents/{id}/sign` — a secretary never uploads or holds a credential of their own. `SigningCredentialPolicy::upload()` allows `rd`/`ard`/`division_chief`, **plus** users in the Records Section division (`Division::recordsSectionId()`) — the latter upload their own P12/e-sig to apply the release stamp below, not to sign as the RD.
- `App\Services\DocumentSigner` applies a PKCS#12 signature onto the PDF by shelling out to `scripts/pyhanko/sign_pdf.py` (Python, the [pyHanko](https://github.com/MatthiasValvekens/pyHanko) library — `App\Services\PyhankoPdfSigner` owns the `Process::run()`/exit-code-translation plumbing, mirroring how `PdfNormalizer` already shells out to `mutool`), verifying the original file's SHA-256 hash first for tamper-evidence. **This replaced an earlier `setasign/fpdi-tcpdf`-based implementation** that silently destroyed any signature already present in a document by the time it reached this step — FPDI's page-import mechanism never reads a source PDF's `/AcroForm` at all, so re-importing pages into a fresh TCPDF document dropped any existing signature dictionary outright, and TCPDF's `Output()` always emits a brand-new single-revision PDF rather than a true incremental update. pyhanko signs via PDF incremental updates instead (the same append-only mechanism Adobe Acrobat itself uses for multi-signer routing) — every signature already in the file (an originator's own PNPKI signature applied externally before upload, a prior RD signature) survives byte-for-byte intact alongside the new one. Requires a Python 3.10+ venv with pyHanko installed — see `scripts/pyhanko/README.md`; the interpreter path is `config('services.pyhanko.python_binary')` / `PYHANKO_PYTHON_BINARY`, following the same env-var-with-PATH-fallback convention as `MUTOOL_BINARY`.
- **Multiple signature placements**: the secretary can place the RD's e-signature image more than once — any number of times on one page, and/or across multiple pages (some documents need every page signed, others just one). Unlike the old TCPDF implementation (which applied one real PKCS#7 signature plus cosmetic-only echo appearances for every additional placement), **each placement is now its own independent, separately-verifiable PDF signature** — `DocumentSigner::sign()` takes an ordered array of `{page, x_percent, y_percent, width_percent}` placements and `PyhankoPdfSigner::apply()`/`scripts/pyhanko/sign_pdf.py` chain them: sign at placement 1 into a temp file, sign that file again at placement 2, and so on, so tampering with one signed page invalidates only that page's signature rather than a single signature that covered everything. `DocumentSignature` (the DB row) still carries `signature_page`/`sig_x_percent`/`sig_y_percent`/`sig_width_percent` mirroring the *first* placement for backward compatibility; the full set lives in the child `document_signature_placements` table via `DocumentSignature::placements()` — this DB shape is unchanged from before the pyhanko migration, since it was always just "what was placed where," independent of how many real cryptographic signatures the resulting file happens to contain. `Documents/Sign.vue` lets the secretary drag/resize a draft box, then explicitly "Add"/"Update"/"Remove" placements one at a time (no bulk "sign every page" shortcut) — at least one is required before submitting.
- **Undoing a signature**: `DocumentPolicy::undoSignature()` lets a secretary revert a `Signed` (not yet `Released`) document back to `Approved` via `DELETE documents/{id}/sign` (`DocumentSignatureController::destroy()`), so a placement mistake can be corrected by signing again through the normal flow — previously this required an admin to manually edit the status in the database. The existing `DocumentSignature` row (and its placements) is never deleted — append-only, matching the rest of this app's audit trail — signing again just creates a new row, and `Document::signature()`'s `latestOfMany()` already always resolves to the newest one. Logged as a `DocumentReview` row (`ReviewAction::SignatureReverted`) and an audit log entry.
- `SignatureAuditLog` (via `App\Services\AuditLogger`) is an append-only, hash-chained (`prev_hash`/`row_hash`) audit trail — never updated, only inserted.
- **Release stamping**: after a document is `signed`, a Records Section user applies a second, separate stamp (their *own* P12 credential + e-signature image, not the RD's) via `documents/{id}/release` (`DocumentReleaseStampController::create/store/download`, `App\Services\DocumentReleaseStamper` — mirrors `DocumentSigner`'s tamper-evidence approach and also now signs via `PyhankoPdfSigner`), producing the final `released` PDF. Tracked in its own `document_release_stamps` table/`DocumentReleaseStamp` model, distinct from the RD's signature. **Before the pyhanko migration this step silently discarded the RD's own signature** too, by the identical FPDI/TCPDF mechanism — meaning `released/*.pdf` (the file Records Section actually downloads and emails out, not `signed/*.pdf`) only ever carried whichever signature was applied last. Now the RD's signature survives into the released file — verified both by `tests/Feature/SignatureChainPreservationTest.php` (asserts the signed file's bytes are an exact prefix of the released file — the mechanical signature of a true incremental update) and manually in real Adobe Acrobat during development.
- **A PDF uploaded with a signature already embedded stays untouched at upload time**: `PdfNormalizer::storeAndHash()` skips its own `mutool clean` rewrite (which would otherwise break the signature's `/ByteRange` hash the same way the old signing pipeline did) whenever `App\Services\PdfSignatureDetector::hasExistingSignature()` finds a `/ByteRange` in the raw file — a cheap raw-byte scan, not a full parse, matching `App\Rules\PdfFile`'s existing `%PDF-` magic-byte-check precedent, and avoiding a Python subprocess on every single upload (uploads vastly outnumber signs).
- **Manual verification step, not automatable**: whenever the signing pipeline changes, sign a real test document twice through the actual app UI (simulating two parties), download the final PDF, and open it in real Adobe Acrobat to confirm both signatures show valid with no corruption warning — no automated test can assert what a real PDF viewer displays. This was the actual go/no-go gate during the pyhanko migration.
- **Marking as emailed**: a lightweight confirmation step after release — Records Section confirms they downloaded the released PDF and sent it out, via `POST documents/{id}/release/emailed` (`DocumentReleaseStampController::markEmailed()`, `DocumentPolicy::markEmailed()`). Deliberately **not** a new `DocumentStatus` (status stays `released`) since it doesn't gate any further workflow action — just `emailed_at`/`emailed_by` columns on `documents`, plus a `DocumentReview` row (`ReviewAction::Emailed`) so it shows in the review/transaction history. `NotificationDispatcher::documentEmailed()` notifies the uploader and their supervisor via the shared private `divisionSupervisors()` helper — checks for a `division_chief` in the document's own division *or its parent* (a document's division can be a sub-unit with no chief of its own, e.g. Procurement Unit under Administrative Division — see the `initialStatus()`/scope notes above), falling back to a `unit_head` in the document's own division when no chief exists anywhere above it (e.g. an ORD sub-unit). `documentSigned()` was refactored to use the same helper — it had the identical "chief not found in a child division" gap before this.
- **`requires_release`** (boolean, defaults `true`): chosen by the originator at submission time (required field in `StoreOutgoingDocumentRequest`/`Documents/CreateOutgoing.vue`) — "yes" means the signed document is meant to be physically released and shows up in Records Section's `ready_to_release` tab (`DocumentScopesTrait::readyToReleaseScope()` and `DocumentPolicy::release()` both gate on it); "no" means it's for the originator's own internal use — it never enters Records Section's queue, and the uploader is simply notified once signed (`NotificationDispatcher::documentSigned()`, unaffected by this flag). Not touched by resubmission — the original choice carries over.

### Divisions
Self-referential hierarchy (`Division.parent_id`). Seeded twice: `RoleAndDivisionSeeder` (idempotent, `firstOrCreate`) then `DivisionSeeder` (**truncates** `divisions` and rebuilds — authoritative in a fresh install, destructive on a live one). Division-code-based logic (`ORD`, `ORDP`, `RS`, etc.) depends on the specific coded row — the dev DB has accumulated some near-duplicate division rows over time (e.g. two "ORD Proper"-ish divisions, only one with a `code`), so when adding division-scoped behavior, verify which row real users are actually attached to rather than assuming by name. `ControlNumberGenerator` (see "Control numbers" above) is another consumer of this same seeded gap — several sub-units (Legal Unit, Procurement Unit, etc.) have no `code` of their own and rely on a parent-code fallback rather than assuming every division is coded.

### File storage
Two **private** local disks, outside the public webroot: `documents` (`storage/app/documents`) and `credentials` (`storage/app/credentials`), configured in `config/filesystems.php`. Files are only ever served through authenticated controller actions (`DocumentController::file()`, `DocumentSignatureController::download()/esig()`, `SigningCredentialController::esig()`) — never via a public URL.

### PDF normalization (system dependency: mutool)
Every uploaded PDF (outgoing submit/resubmit, incoming upload — `OutgoingDocumentController::store()/updateResubmit()`, `IncomingDocumentController::store()`) is passed through `App\Services\PdfNormalizer::storeAndHash()` right after being stored, which shells out to **mutool** (the MuPDF CLI — `mutool clean -d -z -g`) to rewrite the file before its `file_hash` is computed — **unless the upload already contains a digital signature** (`App\Services\PdfSignatureDetector::hasExistingSignature()`; see "Digital signing" above), in which case normalization is skipped entirely to avoid breaking that signature's `/ByteRange` hash. This originally existed because the free FPDI parser (used by `DocumentSigner`/`DocumentReleaseStamper`) cannot read PDF 1.5+ files that use compressed cross-reference/object streams at all — a format many modern "Save/Export as PDF" tools produce by default — previously forcing users to manually re-save affected uploads before they could be signed. **Since the pyhanko migration (see "Digital signing"), the signing pipeline itself no longer uses FPDI and can parse compressed-xref PDFs directly** (verified during that migration's feasibility spike) — so mutool's continued role for *outgoing* uploads is now really just the modest file-size reduction noted below, not a signing prerequisite. `documents:normalize-legacy-pdfs` (below) still targets the old FPDI-compatibility problem specifically and hasn't been revisited — flagged as an open follow-up, not yet decided.
- The binary path is configurable via `MUTOOL_BINARY` in `.env` / `config('services.mutool.binary')` (defaults to relying on `mutool` being on `PATH`). Install with `winget install --id ArtifexSoftware.mutool -e --source winget` — there is no official Ghostscript winget/choco package, and mutool (from the same organization, Artifex) does the same job here.
- **`mutool convert -F pdf`** was tried first and rejected: on a real Canva-exported PDF it silently dropped a background gradient it couldn't correctly recompose (verified by rendering before/after). **`mutool clean -d -z -g`** (decompress, deflate, garbage-collect — not `convert`) was verified to round-trip visually identical output while still eliminating the compressed xref/object streams, plus giving a modest (~1%), always-non-negative file size reduction. Real downsampling/recompression of images (Ghostscript's specialty) isn't available this way — file size reduction here is small.
- Failures (mutool missing, non-zero exit, corrupt input) are logged and swallowed by `PdfNormalizer::normalize()` — the original upload is kept as-is rather than blocking the request, since an unnormalized PDF is still a valid, readable document (it just may fail to sign later, exactly as before this feature existed).
- **Retroactively fixing documents uploaded before this feature existed**: `php artisan documents:normalize-legacy-pdfs` scans outgoing documents not yet `signed`/`released` (already-signed ones are skipped — their signed PDF is a separate file, untouched by this), detects which use compressed xref/object streams via the same FPDI `CrossReferenceException` check that (pre-pyhanko) `DocumentSigner` used to hit, and reports them. Defaults to a dry-run (report only); pass `--apply` to actually rewrite + rehash the affected files. `mutool` must be installed wherever this runs (e.g. the production server), not just in dev.

### Frontend
Vue 3 SFCs under `resources/js/Pages/**`, no client-side router — Ziggy exposes named Laravel routes to JS via the global `route()` helper. `resources/js/Layouts/AuthenticatedLayout.vue` gates nav links by role using the same `page.props.auth.user.roles` array (role-gated nav items must be updated here whenever a policy's allowed-role list changes, or the UI and backend can drift apart — this has already happened at least once in this codebase).
- `Documents/Index.vue` has a mobile-only "quick-preview" bottom-sheet modal (tapping a document card on small screens renders the PDF/image via pdf.js instead of navigating to `Documents/Show.vue`) that also exposes inline Review and Route actions, mirroring what's on the full `Show.vue` page — `DocumentController::index()` decorates each paginated document with `can_review`/`can_route` booleans via `->through()` for this to work without extra round-trips.
- `MagicLinkController` issues a one-time signed login link (admin-generated, RD/ARD only, from `/users`); consuming it (`/magic-login`) logs the user in and, for the `rd` role specifically, redirects straight to `documents.index?tab=for_approval` instead of the dashboard.
- `control_number` is searchable (`DocumentController::index()`'s search where-clause, alongside `reference_number`/division name/uploader) and shown in `Documents/Show.vue`'s Document Details grid plus as muted inline subtext under the title in `Documents/Index.vue` (both the desktop table row and mobile card) — deliberately not a dedicated table column, to avoid squeezing the already-scroll-constrained mobile table further.
